# Echo Simulator Foundation

The memory-only foundation supports a bounded playable V1. The accepted long-term product direction remains [Echo Simulator direction](ECHO_SIMULATOR_DIRECTION.md).

## Ownership

Improve's Current mode continues to read the existing Character-owned build and persistence. Simulate retains a detached source snapshot of the real Character/build for identity, context and isolation, but starts a fresh hypothetical build with exactly five empty active Echo slots. Character identity and non-Echo context (Weapon, Forte and Sequence) are preserved; equipped account Echoes and alternate account Echo sets are excluded from simulated equipment. The sandbox is memory-only. It introduces no storage key, migration, recovery overwrite, equipment commit or competing Character database.

The session uses slots 1–5. The UI maps its existing zero-based selected Echo index at the edge. Any slot can be selected. Each slot owns its candidate, accepted-card history and Trash Pile. The accepted Echo itself lives only in that slot of the sandbox's active set. Manually placed cards populate slots, growing the build from 0 to 5 Echoes. Manual placement is recorded as `placed`, independently of evaluator `accepted` receipts; it never declares Character improvement. Real account cards never seed candidates, accepted history or Trash Piles. Alternate account sets cannot become active simulation equipment. Stats use the existing static projection with sandbox equipment; this is source-backed stat presentation, not usefulness evaluation.

Each candidate has a session-local unique identity, revision, actual card snapshot and detached checkpoint snapshots. Checkpoint recording consumes observed cards. The character-independent `echoSimulatorRolling.ts` adapter uses the existing VerifiedWuwaEchoRuntime to generate those observations; no mechanics or RNG tables are duplicated. The production run driver records canonical public requirement failures as rejected history. Evaluator accepted/rejected receipts remain historical data supplied by an injected future adapter. The same slot history retains successive manually placed cards and any historical accepted cards; rejected history retains the actual card, checkpoints and short supplied reason in the corresponding slot's pile. No name-based keep/discard strategy is used.

Reset restores the preserved non-Echo Character context with a fresh session identity and five empty Echo slots, never the account Echo configuration. Current/exit, Character changes, navigation away from Improve and reload discard the sandbox. Existing real Current Candidate is preserved when entering/exiting Simulate. Current and Simulate share the same editable Improve Settings and Resource Inventory. Settings remain Character-owned; inventory remains a Character-independent user budget in the existing Improve storage envelope. Mode changes create no settings copy. Settings/resource edits cancel active runs without changing real equipment or account Echo sets. Editing saved Resources marks the detached budget stale; Reset explicitly applies the new inputs. Settings are snapshotted for each run; slot, Character, template and Sonata changes cancel work before another attempt. A successful historical card can still be manually placed without claiming it meets newly edited settings.

## Evaluator and production availability

`echoSimulatorBoundary.ts` contains only Pending availability and a small disposition receipt contract. There is no action-policy taxonomy, transport implementation, evaluator endpoint, Character policy, weight or calibration. A receipt must match session, Character, build revision, selected slot, candidate identity and candidate revision. Stale/cross-slot/cross-build receipts fail closed. Identity-only cards cannot be accepted into sandbox equipment.

Future evaluator decisions must be bound to the settings/resource revision under which they were evaluated. Exact mid-run invalidation, re-evaluation and reset semantics remain Pending until that evaluator capability exists; this foundation adds no revision execution, automatic reset or browser re-evaluation.

## Playable requirement runs

Production keeps the Character workspace, **Improve your character → / ← Simulate Echo Set**, and subtle warm mode distinction. **Simulate without a build** selects a released Character without adding account ownership. Recommended/Customize and explicit recovery/reset remain discoverable under **Edit / restore settings**, outside the header.

The settings row starts with **Sonata Sets**, then Target, Gate, Hard Requirements and Flex Stats. Up to two released canonical sets stage a memory-only Character scenario. Selection conveys eligible sets, never a promised bonus or an inferred exact 3+2 assignment. Existing equipped and manually placed cards stay unchanged. Shared Resource Inventory remains the sole persistent budget.

Verified loadout projection supplies cost/main-stat shells and main Echo where reviewed. Augusta uses The False Sovereign and CRIT Rate / Electro / Electro / ATK% / ATK%, with Crown of Valor and Void Thunder eligibility. Remaining identities and Sonata assignments are visibly **editable scenario defaults**, selected deterministically from eligible released catalog entries; they are not reviewed BiS assignments. Characters lacking a reviewed shell get explicitly labeled editable eligible scenario defaults, not recommendations. New Echo changes identity/assigned Sonata; its configuration help changes the cost-valid main stat. Repeated attempts retain one immutable slot template.

**Simulate Echo** acquires complete canonical Rank-5 +25 candidates in cooperative batches of two. Each final card must satisfy **ALL Hard minima AND at least N distinct Flex minima**, through `assessEchoRequirements`. Failed requirements retain actual checkpoint history, spend resources and trigger another attempt. The first success stops and remains in New Echo for inspection and manual placement. Requirement success does not assert Character improvement. Gate remains stored/snapshotted; this V1 evaluates completed +25 cards and implements no earlier rejection policy.

Zero finite Echoes, fewer than 50 finite Tuners, or insufficient whole Tubes stop before acquisition. Invalid/impossible/Pending requirements block before spending. One complete attempt is atomic: canonical Tube spend, separate five tuning transactions and Echo generation are prepared on detached state and committed together. Unsupported mechanics or RNG leave inventory, counters and candidate untouched. Resource exhaustion/cancel are explicit stops; after 1,000 unsuccessful attempts since starting/resuming, a visible **safety pause** preserves the run and offers Resume. Scheduling yields between batches; no uncontrolled loop is used.

The simulation-local inventory uses canonical `ResourceInventory`. A bounded whole-item witness selects the least supplied EXP reaching +25, with equivalent witnesses following canonical Tube catalog order. This explicit V1 driver rule is not a denomination economic ranking, global future-budget optimum, or a change to the canonical frontier optimizer. The existing `spendExactTubes` / `tuneEligibleCheckpoint` engine owns depletion, internal EXP carry, tuning eligibility, cap returns and the last ledger. Counts show actual gross Echoes, Tuners and Gold/Purple/Blue/Green Tubes separately. Verified upgrade overflow returns update working inventory and a separate returned ledger; discard/feed/Data Recovery receipts and net recovery costs remain Pending. No discard refunds are fabricated and saved Resources are never spent by simulation.

All six Resources use the same horizontal scrubber. Click edits an exact safe integer or explicit ∞; drag commits once on release, cancellation restores draft text, and invalid entry retains the previous persisted quantity. Piecewise integer steps add finite soft detent widths at ∞/0/5/10/20, so farther movement always passes. Arrow Up/Down changes one integer, including ∞ below zero; unlimited persists only as the existing domain state. There is no slider bar.

The center presents the main action, immediate status, cancellation/resume and denomination counts. Configuration/economy explanations stay in contextual help; actual checkpoint and slot histories stay on cards. Real build, five-slot isolation and explicit replacement confirmation are preserved. Character evaluation, whole-build completion, recovery-backed restart and global resource optimization remain Pending. UI acceptance and exact-head FULL remain separate gates after user review.

## Resource and mechanics boundary

The visible resource names remain **Tuners | Tubes | Echoes**; raw EXP stays internal. Echo Core and the exact Tube engine own mechanics and actual spending. The run driver composes these existing transactions on a detached budget; no tiers, probabilities, checkpoints, progression or recovery receipts are duplicated. Clearing/replacing never refunds resources. Feed, Data Recovery, Tuner recovery, net recovery costs, Character usefulness and Improvement Cost remain Pending. No combined score, farming probability or completion rule is introduced.

PR #235 remains the evaluator containment boundary, not a replacement UX authority. Customize owns explicit editable choices. Modern verified DEFAULT CALC_BENCHMARK presentation remains the Character Target source; no old PR #224 target data is restored.

Future private evaluation can use the revisioned evolving working build after each accepted Echo to recompute concrete per-stat Target deficit, Every Echo minimums, Build Need and Flex value. Target is a future build goal, not a stat cap. Visual deficit/near-target/reached tolerance bands are not implemented. Recommended minimums may later change with Current, remaining opportunities and Target, but never through fabricated browser thresholds. Independently reviewed hard requirements remain active until satisfied; Calc Target alone cannot establish a hard ER requirement. Flex availability is reviewed relevance, not cross-stat ranking; actual marginal DPS/usefulness ordering needs executable capability. Other Stats retains additional canonical choices. No private weights, calibration or decision policy is restored by these display controls.
