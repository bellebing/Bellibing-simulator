## 1. V1 scope and acceptance

V1 answers: **With these Character goals and my resource budget, what five-Echo build can I achieve, how likely is completion, and what will it cost?** All criteria below are required; a +5 demo, unconditional +25 roller or static prepared-card preview is an intermediate slice.

The current product request resolves two older direction questions: **whole-build simulation and Shell Credits are required in V1**. Reconcile those clauses in the direction/UI contracts when implementing their slices. Preserve the existing card layout, five slots and corresponding Trash Piles, shared components, typography and Current/Simulate separation. Build a Team, account-wide optimization, farming/acquisition probabilities, equipment writeback and a visual redesign remain downstream.

Retain the source-backed Character selector, but enable private decisions only for explicitly advertised capabilities. Augusta/default STAT_TARGET is the first integration pilot, followed by Cartethyia/default only after equivalent evidence. Their existing private pilot status does not satisfy A4–A7. Unsupported ER, mixed trades, cross-stat ranking and team DPS remain Pending; V1 must publish its supported goal dimensions, not claim roster-wide or global-optimum coverage.

## 3. Ownership and execution decisions

**Budget semantics:** Resource Inventory remains the sole persistent, user-entered starting budget. A run takes a versioned, detached working snapshot and spends it atomically with its own candidate/history/ledger. Simulation does not spend the saved starting budget; otherwise repeat runs and Expected trials would consume the user's inputs. This is a planning choice consistent with the memory-only sandbox and spreadsheet Budget/This Run distinction. #249's persistent debit API must not be wired directly into this run. Future real-inventory deduction would require its own durable recovery contract and BUG-045 resolution.

**Edits and lifecycle:** saved Settings/Resources remain editable in both modes. Any relevant edit pauses the run, invalidates outstanding receipts and marks Expected stale; retain cards/history for inspection. Resume under the old basis is disallowed; explicit restart snapshots the new inputs. Reset/exit/reload discards the run, never restores/debits saved budget or changes real equipment. Cancellation stops at a committed action boundary; delayed replies cannot revive a cancelled session. Persistence corruption/write failure preserves recovery bytes and blocks dependent actions. This requires revisions at the canonical input owner, not an independent settings database.

**Template versus result:** keep #249's five editable cards as configuration where that candidate is adopted, visibly distinguished from earned results. Starting a run creates five empty accepted slots. Prepared-card activation/stat previews remain previews; only accepted run cards contribute to run-result stats. Reuse current card components and the existing settings → Simulate navigation; do not create a competing standalone application.

| Public frontend / domain | Private implementation |
| --- | --- |
| Canonical identity, eligibility, RNG, tiers, main-stat growth, exact spend/recovery mechanics after review; character-free Echo Core. | Build Need, trusted Character usefulness, remaining-potential valuation, economic action choice and any proprietary Tube/allocation policy. |
| Input validation, deterministic explicit Hard/Flex acceptance and feasibility; user-owned settings and budget. | Continue/Reject/Accept, temporary retention/replacement, Gate decision semantics, goal/completion policy and allocation across five slots under scarce resources. |
| Neutral run/session transitions, atomic ledger application, five-slot scheduling of authorized actions, card history, static stats and safe reason/status presentation. | Capability approval, independently assembled comparisons, context/source validity, weights/calibration and private policy orchestration. |
| Wire-safe versioned requests/results and aggregation/display of safe trial outputs; approved public asset list and generated parity. | Repeated policy execution for Expected; private analytical references may corroborate results but cannot substitute for exact inventory execution. |

Extend the small existing boundary with only required safe fields: run/session, Character/context, source/build/settings/resource/candidate revisions, slot, action/idempotency identity, mechanics and evaluator/policy versions, supported capability, disposition/stop status and safe reason. Require a proposal bound to exact input state before commit; stale, unknown or mismatched replies commit nothing. Do not publish policy internals or import legacy public strategy advice as a fallback.

## 5. Expected results contract

Expected is a distribution of **the same complete run**, not a Recommended target or an average of selected successful rolls. Freeze a run manifest containing all five templates, non-Echo context, explicit requirements/goal, starting quantities, recovery mode, policy/mechanics versions, slot policy, seed scheme and stopping limits.

- Budget report: mean final stat vector and completed-slot count over all valid trials, including exhausted partial builds; probability of five requirement-qualified cards and of the full Character goal separately. Also show conditional-on-completion stats, clearly labelled with their sample count.
- Costs: gross spending, recovery receipts and remaining counts by Echoes, Tuners, Shell Credits and each Tube denomination; mean and P50/P90 for a declared population. Report within-budget consumption separately from resources needed to complete. Do not subtract receipts invisibly or price resources with arbitrary weights.
- Completion-cost experiment: same policy and mechanics, with explicitly declared budget constraints relaxed or raised. Report only completed-trial cost quantiles plus the noncompletion/censoring rate and horizon; these are conditional estimates, not a guaranteed sufficient inventory or an unconditional cost-to-finish. Mixed denomination budgets have no single universal “required resources” vector. Offer probability at the user's actual budget as the primary actionable result.
- Use independent seeded Monte Carlo trials for V1, with at least 10,000 valid trials for the standard report; record sample count and a 95% completion-probability interval. Show sampling uncertainty for mean stats/costs. Zero observed successes is not mathematical impossibility; report the interval, and leave completion-conditioned values unavailable.
- Every unlimited run has an explicit attempt/work horizon and cancellation. A safety cutoff is censored, not a gameplay failure. Report censored/blocked trials separately; source/service errors make the report incomplete rather than entering the success denominator. Exact impossibility requires a deterministic proof from the applicable contract.
- Changing inputs invalidates the report. A comparison to the actual run requires matching manifests; its percentile is per resource and population. Interactive, Auto and headless trials share one action driver and private policy. No independently simplified Expected formula path.
