# Character raw verification gaps — Worker 13 pilot

**Review date:** 2026-10-11. **Baseline:** `main` of `bellebing/Bellibing-simulator`; Worker 6's unmerged Draft [PR #257](https://github.com/bellebing/Bellibing-simulator/pull/257) is **review evidence, not merged main**. Scope is the Character *raw* record, not BiS, profile recommendations, Character Mechanics execution, DPS or UI acceptance. No status or number is promoted by this document.

## 1. What `VERIFIED` actually requires

`src/contentRegistry.ts` defines `VERIFIED | PARTIALLY_VERIFIED | PENDING`, but there is **no code predicate that automatically grants `CharacterGameData.VERIFIED`**. `src/data/characters.ts` explicitly defaults rows to `PARTIALLY_VERIFIED` and describes V9.15 imports as awaiting a *full Character base audit*; Augusta is the manually designated golden reference. A populated record and a green completeness audit therefore do **not** satisfy a verification decision.

There are two separate thresholds:

1. **Mechanical completeness (enforced):** `src/data/characterRawAudit.ts` checks the nine released-Character fields `element`, `weaponType`, Level-90 `hp`, `atk`, `def`, `maxEnergy`, plus `baseCombat.critRate`, `critDamage`, `energyRegen`. A `null` must have a character/field-specific dated exception in `RELEASED_CHARACTER_RAW_PENDING`; unexpected missing, stale exceptions and unknown pending Character IDs are errors. This is a null/exception consistency audit, **not** a source-review or promotion test. It does not audit rarity, release status, numeric accuracy, source freshness or intrinsic nodes.
2. **Source-validity decision (manual):** under `docs/DATA_VERIFICATION_POLICY.md` and `docs/CONTENT_PREFLIGHT_AND_IMPACT_AUDIT.md` A1–A2, verify stable identity/rarity/element/weapon/release, the exact **game-facing Level-90 integer convention** for HP/ATK/DEF, the semantically labeled **Max Energy cap** (never substitute Liberation Resonance Cost or ambiguous `Energy`), base CRIT Rate/CRIT DMG/ER, and permanent Minor-Forte/intrinsic nodes. Retain traceable, dated sources **per disputed field**, resolve material differences or leave them pending, and record an explicit reviewer decision. This is sufficient to *consider* `VERIFIED + DATA_ONLY`; it does not imply integration, modeled effects, source-verified mechanics, executable rotations or DPS readiness. A subsequent real data change requires its appropriate backward-impact audit.

Bellibing's policy gives the **Prydwen all-Resonator Level-90 Stats table** precedence as the consistent Prydwen integer surface; individual Prydwen profile values are secondary. Structured progression decimals may explain adjacent `±1` presentations but cannot justify an invented global rounding rule. Prydwen source **URLs printed by the default `row()` constructor are provenance leads**, not evidence that someone reviewed all nine values: by default every imported row inherits `['V9.15 Characters', 'Prydwen']`, an individual Prydwen URL, and `checkedAt: 2026-08-23`. The three base-combat values are likewise common `row()` literals (`0.05`, `1.5`, `1`), not individual measurements. `characterIntrinsicStats.ts` has independently `VERIFIED` Minor-Forte rows with its own provenance; its verification does not automatically change the enclosing Character row's status.

## 2. Why so many rows remain partial

Worker 6's [fact matrix on Draft #257](https://github.com/bellebing/Bellibing-simulator/blob/research/worker-6-character-build-data-coverage-20261011/docs/research/CHARACTER_FACTS_COVERAGE.md) reconciles **59 RELEASED**, **54 with all four Lv90 numbers present**, and **only Augusta at whole-raw `VERIFIED`**. Thus **53 numerically complete rows remain `PARTIALLY_VERIFIED`**. It is incorrect to count these as 53 missing raw-stat sets. The five *actually incomplete* released rows are Hsin/Jingran (HP/ATK/DEF/Max Energy all null), plus Qingxiao/Rover Electro/Suisui (`maxEnergy` null under explicit semantic exceptions). Upcoming Suoming is outside the released denominator.

Root-cause buckets: **(A) historical status debt:** V9.15 migration intentionally kept populated rows partial pending record-wide review; **(B) evidence/decision gap:** the default source label/date is generic, not a per-field checked resolution, while separate intrinsic/mechanics/source-UI reviews were not rolled up into Character raw decisions; **(C) real missing data:** the five named released cases have audited nulls; **(D) semantic/presentation tension:** Max Energy versus Liberation cost is a true semantic hazard, while adjacent displayed Lv90 integers may simply reflect distinct conventions. Disagreements already documented outside this pilot (for example Mornye's 10% versus 12% Healing Bonus intrinsic/UI source and Brant's 125/140 energy-label concern) must not be silently generalized or resolved by batch promotion.

The existing Character Truth Factory capture (`docs/CHARACTER_TRUTH_CAPTURE.md`) is **noncanonical evidence**. Captured values, reconciliation consensus, and Worker 6's independently VERIFIED ACTIONS/FORTE/Inherent/Mechanics audit areas are valuable *reuse inputs*, not substitutes for a specific Character raw source decision. `characterRawAudit.ts` lists **no pilot-field exception**: all five pilot rows pass null completeness solely because their nine required fields are non-null.

### Source evidence vs. verification decision

**Evidence established:** four pilot Characters (Chisa, Cartethyia, Ciaccona, Iuno) have all nine non-null raw-audit fields, independent intrinsic VERIFIED rows, and matching *roster-convention* Level-90 stats from the preferred published raw-stat surface. Denia's 100/125 named Max Energy discrepancy requires a targeted, higher-confidence semantic review before that queue can approve the entire row. None of the five is promoted here.

## 4. Efficient remaining-roster audit (reuse-first)

1. **Join by existing canonical Character ID**: start from `characters.ts` + `characterRawAudit.ts`; annotate the nine fields, identity/rarity/release, `characterIntrinsicStats.ts` status, raw provenance and field-specific disputes. Reuse Worker 6's #257 roster matrix and existing source snapshots/reviews as *evidence pointers*, never create a copied Character value catalog.
2. **Prioritize blockers separately**: Hsin/Jingran need actual Lv90 progression data; Qingxiao/Rover Electro/Suisui need Max Energy semantic resolution; Denia now has a pilot **source discrepancy to investigate**. These do not belong in the same queue as populated status debt. Keep Brant's energy header and Mornye's intrinsic discrepancy independently flagged; neither is silently waived.
3. **Batch common source families, sign off individual records**: use the Prydwen **Stats roster** for a consistent Lv90 integer convention; use existing pinned original game tree and Prydwen Minor-Forte profiles for intrinsic/base checks; validate source meaning, release freshness and pertinent exceptions. A single common-source review may cover many equal-valued fields, but each Character needs documented field coverage + dated reviewer disposition. Add exact URL/version/check date or stable pinned capture, and explicitly record adjacent integer displays as presentation or real conflicts.
4. **Keep a review decision ledger, not a new runtime table**: track Character ID → raw fields checked/source refs → semantic exception(s) → reviewer/date → *proposed* status, ideally within bounded research/evidence notes adjacent to existing owner. Only a later authorized source/data PR should update `characters.ts` provenance/status and any affected pending exceptions; run the focused raw completeness/intrinsic/preflight and backward-impact checks there. Gameplay, profiles, modeling and integration status remain separate.
5. **Stop re-reviewing unrelated facts**: source-VERIFIED ACTIONS/FORTE/Sequence/Mechanics from Worker 6 and existing canonical audits remain valid in their own domains unless their provenance drifts or new contradictions appear. Neither their success nor an unmerged report changes raw `verificationStatus` automatically.
